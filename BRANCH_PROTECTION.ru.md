# Рекомендации по защите ветвей и выпуску

В этом документе описаны рекомендуемые настройки управления репозиторием для `outlookEmail`.

## Цель

Предотвратите случайную прямую разработку на `main`, уменьшите шумную деятельность по выпуску/сборке и сделайте выпуски более предсказуемыми.

## Рекомендуемые роли ветвей

- `main`: ветка стабильной версии.
- `dev`: ветка разработки по умолчанию.

## Рекомендуемая защита ветвей GitHub

### Защитите `main`

Рекомендуемые настройки:

- Требовать запрос на включение перед объединением
- Требуется как минимум 1 одобрение (необязательно, если обслуживается в одиночку, но рекомендуется, если соавторы присоединятся позже)
- Отклонять устаревшие утверждения при отправке новых коммитов.
- Требовать прохождения проверок статуса перед объединением
- Требовать, чтобы ветки были обновлены перед слиянием.
- Ограничить прямые нажатия `main`.
- Ограничить силовые нажатия
- Ограничить удаление веток

### Рекомендуемые обязательные проверки для `main`

Как минимум:

- `build-and-push`

Если позже будут добавлены дополнительные проверки CI, включите их сюда.

### Защитите `dev`

Рекомендуемые более легкие правила:

- Разрешить прямые отправки, если репозиторий в основном обслуживается в одиночку.
- Запретить принудительные нажатия, если это явно не требуется.
- Опционально потребуйте PR для более крупных рискованных изменений.

## Рекомендуемый ежедневный рабочий процесс

1. Разработка на `dev`
2. Внесите дополнительные изменения в `dev`.
3. Проверьте поведение приложения/статус CI.
4. Объединить `dev` с `main` только для освобождаемых состояний.
5. Обновление `VERSION` и `CHANGELOG.md`.
6. Нажмите тег версии, например `v1.0.1`.

## Создать политику триггера

Чтобы избежать чрезмерной публикации изображений:

- Сборки Docker должны запускаться только для изменений, связанных с кодом/средой выполнения/контейнером.
- Изменения только в документации не должны вызывать пересборку образа.
- Создание релиза GitHub должно происходить только по тегам `v*`.

Текущая политика репозитория реализована в Действиях:

- `docker-build-push.yml` срабатывает при:
  - Изменения исходного кода Python
  - `requirements.txt`
  - `Dockerfile`
  - `.dockerignore`
  - `templates/**`
  - изменения в файле рабочего процесса
- Он запускает триггер **not** для изменений README / журнала изменений / только для выпуска документации.

## Политика выпуска

- `main` представляет готовый к выпуску код.
- Теги версий (`vX.Y.Z`) обозначают официальные выпуски.
- Примечания к выпуску GitHub должны быть взяты из `CHANGELOG.md`.
- Избегайте добавления тегов, если `VERSION`, `CHANGELOG.md` и фактически поставляемый код не синхронизированы.

- Добавьте тестовый рабочий процесс и запросите его на `main`.
- Добавлено ручное одобрение публикации рабочих изображений.
