#Руководство по обновлению

Этот документ предназначен для пользователей, которые уже используют этот проект, и объясняет шаги обновления, предложения по резервному копированию и идеи отката после выпуска новой версии.

## Рекомендации перед обновлением

Перед обновлением рекомендуется выполнить следующие операции:

1. Создайте резервную копию каталога `data/`, по крайней мере, сохраните файлы базы данных.
2. Запишите используемые в данный момент теги образа, методы развертывания и ключевые переменные среды.
3. Подтвердите, что текущий `SECRET_KEY` будет по-прежнему сохранен и не будет заменен во время обновления.
4. При использовании обратного прокси-сервера или автоматического сценария убедитесь, что порт, имя домена и путь не изменились после обновления.

## Ключевые данные, которые необходимо сохранить

Самое важное, что следует учитывать при обновлении, — это сохранить следующее:

— База данных SQLite: `data/outlook_accounts.db`.
- Исправлен `SECRET_KEY`
— Пользовательские переменные среды

Если `SECRET_KEY` изменен, сохраненные конфиденциальные данные, такие как токен обновления, ключ API и пароль электронной почты, не смогут быть расшифрованы.

##3.0.30 инструкция по обновлению

- Исправлена ​​проблема неправильного чтения сведений, вложений или случайного удаления других писем из-за изменения серийного номера после удаления писем IMAP. Список возвращает UID единообразно; когда сервер предоставляет UIDVALIDITY, идентификатор равен `imap:<UIDVALIDITY>:<UID>`, и клиент API должен повторно синхронизировать список и вернуть идентификатор как есть.
- старые запросы `id_mode=sequence` предлагают обновить список; вернуть ошибку, если целевой UID не существует и больше не читает и не обрабатывает другие сообщения с тем же номером.
— Старый тег кэша IMAP будет признан недействительным и перестроен посредством синхронизации при первом запуске. Исходная запись тела кэша по-прежнему будет сохраняться в базе данных для восстановления; учетные записи, авторизация, кэш графа и удаленная почта не будут затронуты. Пожалуйста, сохраните исходную базу данных и SECRET_KEY.
– Gmail, Outlook IMAP и другие почтовые ящики, не поддерживающие сортировку, теперь могут использовать общий доступ «Только последние N». Возврат к сортировке по времени после чтения метаданных UID и INTERNALDATE, копирование или импорт старых сообщений не меняет значение времени для слова «последние».
— Сканирование большого почтового ящика с откатом может занять больше времени, и все сканирование использует текущий бюджет тайм-аута IMAP; неполная проверка или тайм-аут по-прежнему будут отказывать в доступе, а разрешения на общий доступ не будут расширены.

##3.0.29 инструкция по обновлению

— во всплывающие окна добавления и редактирования учетной записи Outlook/Hotmail добавлена ​​новая область токена, и вы можете выбрать автоматический режим, `.default`, только для чтения, полные разрешения или настройку; поля базы данных будут автоматически заполнены при первом запуске, а существующие учетные записи по умолчанию останутся в автоматическом режиме без ручной миграции.
- Автоматический режим запоминает успешные скоупы в процессе; при изменении конфигурации или автоматическом восстановлении старый кеш будет очищен, и конфигурация учетной записи будет напрямую применена к фоновой пересылке. Отправка, удаление и пометка как прочитанные по-прежнему требуют соответствующих разрешений от Microsoft.
— Ограниченный общий доступ к электронной почте заменен на отложенную загрузку по папке, и во входящих и спаме отображаются только последние N писем.
- **Старая ссылка с ограниченным общим доступом также изменится с «Всего N сообщений для обеих папок» на «N сообщений для каждой папки», при этом будет доступно максимум 2N сообщений. Пожалуйста, просмотрите существующие ссылки перед обновлением; Если вы не принимаете новый диапазон видимости, вам следует сначала отозвать ссылку. **

##3.0.28 инструкция по обновлению

— Правила пересылки теперь могут устанавливать ключевые слова электронной почты и отправителей отдельно, что применимо как к обычным почтовым ящикам, так и к источникам Cloudflare; адрес отправки SMTP и конфигурация целевого получателя канала уведомлений остаются неизменными.
— Управление пересылкой поддерживает однократное и пакетное редактирование одного и того же исходного диапазона. Пакетное редактирование изменяет только отмеченные поля, а неотмеченные поля сохраняют свои исходные значения; оставив поле пустым после проверки условия, можно очистить его.
— при первом запуске автоматически заполняются поля условий правил для существующей базы данных и переносятся старые глобальные ключевые слова в обычные правила почтовых ящиков, действовавшие до обновления; Cloudflare по-прежнему не будет использовать старые глобальные ключевые слова. Если миграция не удалась, она будет отменена, и нет необходимости вручную выполнять миграцию базы данных.
— Установленные поставки не будут автоматически повторно отправляться из-за последующего изменения условий правил; перед обновлением рекомендуется создать резервную копию каталога `data/`.

##3.0.27 инструкция по обновлению

— Настройки пересылки электронной почты были реструктурированы в независимое рабочее пространство управления «Пересылка электронной почты». После обновления конфигурациями можно будет управлять отдельно в каналах уведомлений, правилах переадресации, истории доставки и текущих настройках.
— При первом запуске таблицы данных, связанные с пересылкой, будут автоматически созданы, а старые настройки SMTP, Telegram, Enterprise WeChat и Feishu будут перенесены идемпотентно как совместимые каналы, что устраняет необходимость вручную выполнять миграцию базы данных.
— Существующие обычные почтовые ящики, в которых изначально была включена переадресация, будут перенесены на свои собственные правила для почтовых ящиков и связаны с исходным каналом; учетные записи, которые изначально отключили переадресацию, останутся без уведомлений; существующие созданные вручную учетные записи, группы или правила Cloudflare не будут перезаписаны.
— при миграции сохранится эффективное время канала, курсор пересылки и запись об успешном выполнении. Перед обновлением по-прежнему рекомендуется создать резервную копию каталога `data/`; Если вам нужно выполнить откат, сначала остановите планирование новой версии и убедитесь, что старая версия не может обрабатывать новые экземпляры пересылки и уведомления Cloudflare.

##3.0.21 инструкция по обновлению

— Автоматическое добавление полей результата ротации обновления и времени последнего успешного обновления при первом запуске, что устраняет необходимость вручную выполнять миграцию базы данных.
— Самое последнее время успеха существующей учетной записи будет восстановлено на основе журнала успехов и статуса учетной записи; результат ротации, не записанный в старый журнал, отображается как «Незаписанный», а время, которое невозможно подтвердить, отображается как `-`.
- «Недавнее обновление» содержит успешные и неудачные попытки; «Недавнее успешное обновление» содержит случаи, когда запрос не был ротирован, но был успешным; «Недавняя ротация» обновляется только при успешном сохранении нового токена обновления.

## Обновление Docker

### Обновитесь до последней стабильной сборки ветки.

```bash
docker pull ghcr.io/assast/outlookemail:latest
docker compose down
docker compose up -d
```

### Обновление до указанной официальной версии

В официальной среде рекомендуется отдавать приоритет использованию четких номеров версий:

```bash
docker pull ghcr.io/assast/outlookemail:v2.0.15
docker compose down
docker compose up -d
```

Если вы используете `docker-compose.yml`, вы также можете напрямую изменить изображение на указанную версию:

```yaml
services:
  outlook-mail-reader:
    image: ghcr.io/assast/outlookemail:v2.0.15
```

Выполнить после завершения:

```bash
docker compose up -d
```

## Обновление Windows `exe`

### Онлайн-обновление

1. Войдите в приложение и откройте информацию о версии вверху страницы.
2. После обнаружения новой версии нажмите «Обновить сейчас», чтобы подтвердить запуск.
3. Дождитесь завершения загрузки, распаковки и перезагрузки; на этапе загрузки будет отображаться процент, размер и скорость, а также разрешена отмена.
4. Текущая страница автоматически обновится и отобразит новую версию после восстановления службы.

Онлайн-обновление по-прежнему использует существующий `OutlookEmail-windows-x64-X.Y.Z.zip` в выпуске GitHub, и дополнительный установщик загружаться не будет. Файл обновления временно сохраняется в каталоге, где находится текущий EXE-файл, поэтому каталог должен позволять текущему пользователю создавать, переименовывать и удалять файлы; программа не будет подавать заявку на повышение привилегий UAC.

Если версия хранилища была обновлена, но соответствующий ZIP-архив еще не выпущен, на странице будет предложено повторить попытку позже, и текущая программа не завершится.

### Обновление вручную

Если онлайн-обновление недоступно, вы все равно можете использовать исходный метод:

1. Загрузите новую версию `OutlookEmail-windows-x64-*.zip` с GitHub Releases.
2. Выходим из старой программы.
3. Извлеките файлы в новый каталог или перезапишите файлы программы в старом каталоге.
4. Сохраните исходный каталог данных `%APPDATA%\\OutlookEmail`.
5. Запустите новый `OutlookEmail.exe`.

Описание:

- Данные по умолчанию находятся не в каталоге программы, а в `%APPDATA%\\OutlookEmail`
- Не удаляйте файлы базы данных или ключей в этом каталоге.
- Онлайн-обновление сначала создает резервную копию старой программы в `*.old.exe` в том же каталоге, а затем удаляет ее после подтверждения того, что новая версия успешно прослушивает веб-порт.
- Если новая версия не может быть запущена, старая версия будет автоматически восстановлена; если произошло отключение электроэнергии или процесс принудительно завершен системой во время замены, вы можете выйти из соответствующего процесса и вручную изменить `*.old.exe` обратно на исходное имя EXE-файла.

```bash
git pull origin main

```

Если вы используете виртуальную среду, активируйте соответствующую среду перед выполнением.

## Проверка после обновления

После обновления рекомендуется подтвердить как минимум следующее:

1. Страницу входа можно открыть в обычном режиме.
2. Исходные учетные записи, группы, ярлыки и настройки все еще существуют.
3. Исходная плоская группа по-прежнему отображается как группа первого уровня; создание новой подгруппы и выбор родительской группы для просмотра учетной записи подгруппы — это нормально.
4. В произвольном порядке проверьте хотя бы одну учетную запись Outlook и одну учетную запись IMAP на предмет нормального доступа.
5. Если внешний API включен, проверьте `/api/external/emails` один раз.
6. Если включена автоматическая пересылка или запланированное обновление, проверьте, нормально ли выполняется задача.

## Идеи отката

Если после обновления обнаружены проблемы, вы можете выполнить откат в соответствии с исходным методом развертывания:

### Откат Docker

```bash
docker pull ghcr.io/assast/outlookemail:v2.0.13
docker compose down
docker compose up -d
```

### Откат Windows

- Вернитесь к старой версии `exe`.
— Оставить исходный каталог данных без изменений.

### Откат Python

```bash
git checkout <соответствующая фиксация или тег старой версии>
pip install -r requirements.txt
python web_outlook_app.py
```

Если структура базы данных изменится в процессе обновления, перед откатом необходимо сначала подтвердить, совместима ли старая версия с текущей базой данных.

## Часто задаваемые вопросы

### Ошибка входа в систему или сбой конфиденциальных данных после обновления.

Установите приоритет проверки того, был ли изменен `SECRET_KEY`. Это самая распространенная причина.

### После обновления версии `latest` и Release несовместимы.

Это нормально:

— `latest` обычно соответствует последней соответствующей сборке ветки по умолчанию.
— `vX.Y.Z` соответствует образу версии, созданному при выпуске официальной версии.

Для официальной среды рекомендуется указать четкий номер версии.
