# Примечания к выпуску

Этот документ используется для описания стандартного процесса выпуска, правил нумерации версий, поведения действий GitHub и этапов проверки этого хранилища после выпуска.

## Область применения

- Ветка ежедневной разработки: `dev`.
- Стабильная ветка выпуска: `main`.
- Метка версии автоматически выпущена: `git push origin vX.Y.Z`.
- Рабочий процесс публикации вручную: `Create GitHub Release`

## Version number rules

Проект принимает семантический номер версии:

- `MAJOR.MINOR.PATCH`
- Пример: `2.0.15`

Соглашение:

- Нажатие тега Git в форме `v2.0.16` автоматически запускает рабочий процесс выпуска.
- При публикации действий GitHub вручную введите номер версии без `v`, например `2.0.15`.
- Рабочий процесс автоматически создаст соответствующую метку `v2.0.15`.
- Название версии в `CHANGELOG.md` также должно быть записано как `## [2.0.15] - 2026-04-15`.

## Выпущенные продукты

После отправки тега версии или ручного запуска рабочего процесса `Create GitHub Release` автоматически будут созданы следующие продукты:

- Тег Git: `vX.Y.Z`
- Релиз на GitHub: под названием `vX.Y.Z`.
- Сжатый пакет рабочего стола Windows: `OutlookEmail-windows-x64-X.Y.Z.zip`
- Установочный пакет macOS: `OutlookEmail-macos-x64-X.Y.Z.dmg`, `OutlookEmail-macos-arm64-X.Y.Z.dmg`
- Образ Docker: `ghcr.io/assast/outlookemail:vX.Y.Z`.

Дополнительное объяснение:

- Теги `latest` / `main` / `dev` поступают из рабочего процесса Docker, запускаемого при отправке ветки.
- Рабочий процесс выпуска отвечает за выпуск образа версии `vX.Y.Z`.
- Текст релиза GitHub сначала извлекает соответствующие записи версии из `CHANGELOG.md`.

## Предварительная проверка

Перед публикацией рекомендуется проверять каждый пункт:

1. Целевой коммит был объединен с `main`, а `main` находится в состоянии, готовом к выпуску.
2. `VERSION` обновлен до этого номера версии.
3. `CHANGELOG.md` добавил запись для этой версии с полной датой и содержанием.
4. Если вам нужно напомнить пользователям о новых функциях, копия `releaseNoticeModal` в `templates/partials/index/dialogs-management.html` была обновлена.
5. Описания поведения, включенные в `README.md`, документы по развертыванию и документы по обновлению, не противоречат текущей реализации.
6. Если это изменение затрагивает Docker, Windows `exe`, переменные среды, API или взаимодействие с внешним интерфейсом, документ был написан синхронно.

## Стандартные этапы выпуска

### 1. Полная разработка и проверка функций в `dev`.

Рекомендуется сначала завершить функции, исправления и организацию документации в ветке `dev`, а затем объединить ее с `main`.

### 2. Объединено с `main`

Убедитесь, что фиксация `main` является окончательным кодом, готовым к выпуску.

### 3. Обновите номер версии.

Синхронно обновить следующий контент:

- `VERSION`
- `CHANGELOG.md`
- `releaseNoticeModal` копирайтинг в `templates/partials/index/dialogs-management.html` (если нужно предлагать пользователям новые возможности)

Пример:

```txt
VERSION            -> 2.0.15
Заголовок CHANGELOG.md -> ## [2.0.15] - 15 апреля 2026 г.
```

### 4. Отправьте и нажмите `main`.

```bash
git checkout main
git pull
git add VERSION CHANGELOG.md README.md RELEASE.md docs/
git commit -m "docs: prepare release 2.0.15"
git push origin main
```

Если этот выпуск также содержит изменения кода, отправьте файлы кода вместе.

### 5. Нажмите тег версии, чтобы активировать автоматический выпуск.

```bash
git tag -a v2.0.16 -m "Release v2.0.16"
git push origin v2.0.16
```

После отправки рабочий процесс `Create GitHub Release` автоматически запустится и опубликует версию.

### 6. Вручную запустить рабочий процесс выпуска GitHub (неформально)

Если вы не хотите запускать его путем отправки тега или вам нужно перевыпустить определенную версию, вы также можете войти в GitHub Actions и запустить ее вручную:

- Имя рабочего процесса: `Create GitHub Release`.
- Входные параметры: `version`
- Пример ввода: `2.0.15`

Не заполняйте `v2.0.15`, иначе будет сгенерирована метка ошибки.

## Фактическое содержание рабочего процесса.

Рабочий процесс `Create GitHub Release` будет последовательно выполнять следующие этапы:

### 1. Сборка Windows `exe`

- Используйте `pyinstaller --noconfirm --clean outlookEmail.spec`
- Пакет `dist/OutlookEmail.exe`
- Сжато с помощью `README.md` в качестве фиксатора.

### 2. Сборка macOS DMG

- Запуск `scripts/build-macos-dmg.sh` на macOS x64 и Arm64 Runner
- Используйте PyInstaller для создания `OutlookEmail.app`.
- Используйте `hdiutil` для создания вложений публикации DMG, которые можно перетаскивать и устанавливать.

### 3. Создание и отправка тегов

- `vX.Y.Z` будет создан автоматически при запуске вручную.
- Когда активируется передача тега, текущий отправленный `vX.Y.Z` будет напрямую использован повторно.
- Если тег с таким именем уже существует и указывает на текущую отправку, создание будет пропущено.
- Если тег с таким же именем существует, но указывает на другой коммит, рабочий процесс завершится сбоем и публикация прекратится.

### 4. Создание примечаний к выпуску

Рабочий процесс извлечет содержимое, соответствующее текущей версии, из `CHANGELOG.md`:

- Формат соответствия: `## [X.Y.Z]`.
- Если совпадение не найдено, будет использовано очень короткое описание по умолчанию.

Поэтому перед официальным выпуском вам следует убедиться, что `CHANGELOG.md` заранее написал запись для этой версии.

### 5. Создайте и отправьте образ версии Docker.

Рабочий процесс вызывает `docker-build-push.yml` и построен на основе тега `refs/tags/vX.Y.Z`:

- `ghcr.io/assast/outlookemail:vX.Y.Z`

### 6. Выпуск релиза на GitHub

В конечном итоге будет создан официальный выпуск, и будет загружен сжатый пакет Windows и вложение DMG для macOS.

## Проверка после выпуска

Рекомендуется проверить как минимум следующие пункты:

1. Страница выпуска GitHub создана с правильным заголовком и телом.
2. Вложение к выпуску можно загрузить, а имя файла содержит номер версии.
3. `vX.Y.Z` существует во вкладке «Склад».
4. Образы извлекаемых версий в GHCR:

```bash
docker pull ghcr.io/assast/outlookemail:v2.0.15
```

5. Если эта версия содержит изменения в развертывании или интерфейсе, протестируйте тестовую среду, чтобы убедиться в успешности обновления.

## Часто задаваемые вопросы

### Почему текст релиза GitHub неполный?

Обычно название соответствующей версии не записано в `CHANGELOG.md` или формат названия не совпадает. Пример правильного формата:

```md
## [2.0.15] - 2026-04-15
```

### Почему метка приглашения рабочего процесса уже существует, но SHA несовместим?

Указывает, что тег с таким же именем был применен к другим материалам. В это время не продолжайте форсировать выпуск. Сначала вам следует подтвердить:

- Используются ли на этот раз повторяющиеся номера версий?
- `main` Произошли ли дополнительные фиксации
- Были ли исторические теги созданы неправильно

### Почему изображение `latest` не обновляется?

Поскольку рабочий процесс выпуска выпускает только образ `vX.Y.Z`. `latest`/`main`/`dev` происходят из рабочего процесса Docker, запускаемого при отправке ветки, а не из рабочего процесса выпуска.

## Рекомендуемая частота выпусков

1. Обычно разрабатывают и ремонтируют в `dev`.
2. Объединен с `main`, когда будет готов к выпуску.
3. Сначала заполните `CHANGELOG.md` и связанные с ним документы, а затем нажмите тег `vX.Y.Z`, чтобы активировать автоматическое освобождение.
4. После выпуска используйте образ `vX.Y.Z` для фактической проверки развертывания.
